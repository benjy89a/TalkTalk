# E-3 최근 10개 요약 시간 초과 조사 — 2026-11-23

## 확인된 사실과 한계

- 사용자 제보: 배포된 TalkTalk에서 최근 10개 요약도 시간 초과. 로그인된 브라우저 제어 연결이 없어 그 탭의 요청 상태·경과 시간·선택 채널·본문 길이는 직접 확인하지 못했습니다. 비밀번호·쿠키를 받거나 계정 데이터를 다른 경로로 추출하지 않았습니다.
- 이전 `createExaoneSummary` 기본값은 **25초**였습니다. E-4 할 일 추출의 240초 설정과 별개입니다. 요약 route에는 `maxDuration`이 없었습니다. 기본 배포 한도가 얼마인지는 코드만으로 알 수 없습니다.
- 클라이언트 `summaryClient`는 별도의 25초 타이머가 없습니다. 서버의 `AI_TIMEOUT`은 자체 타이머 만료 또는 업체의 HTTP 408/504에서 반환됩니다. 같은 코드이므로 **해당 오류 문구만으로 어느 쪽인지 확정할 수 없습니다.**
- 메시지 10개라는 개수만으로 요약 시간을 보장할 수 없습니다. 각 메시지 길이·추론/최종 출력량·업체 처리 상황 등이 다릅니다. 공식 문서상 모델은 항상 추론을 하며, 이미 `reasoning_effort: "low"`입니다. `stream: false`이므로 완성 전에는 UI에 요약 본문이 나타나지 않습니다.
- 키 오류·요금제·대기열·네트워크 중 특정 원인이 확인된 것은 아닙니다. 무료 API라 항상 느리다고 단정하지 않습니다.

## 실제 업체 검사 (합성 대화만, 정확히 2회, 자동 재시도 없음)

같은 가상의 시연 준비 대화 10개, 같은 프롬프트·모델·출력 상한으로 검사했습니다. 로그인된 앱 API나 DB를 거친 검사가 아닙니다.

| 설정 | HTTP | 경과 시간 | 종료 사유 | 내용 확인 |
|---|---|---|---|---|
| 이전 25초 | 200 | 10,923ms | stop | 날짜·로그인 점검·검색 점검·발표자 미정·추론 마크업 없음 5개 확인 |
| 중간 제안 120초 | 200 | 12,544ms | stop | 같은 5개 확인 |

둘 다 25초 안에 성공했습니다. **사용자 실패의 실제 재현이나 “제한 변경으로 실서비스가 해결됨”의 근거가 아닙니다.** 이후 사용자 요청으로 **요약·AI 검색·할 일 추출 모두 240초로 통일**했습니다. 120초는 조사 중간 설정이며 240초 변경 후 추가 실제 AI 호출은 하지 않았습니다. 배포본에서 아래 확인이 남아 있습니다. 이 5개 확인만으로 전체 품질·환각 없음·지시 공격 방어를 보장하지 않습니다. 실제 대화·키·인증 헤더·업체 원문/추론은 로그에 남기지 않았습니다.

## 이번 보완

1. `SUMMARY_TIMEOUT_MS = 240000`: 요청부터 응답 본문 읽기까지 240초. AI 검색·할 일 추출·관리자 연결 테스트도 동일합니다. 기존 2,048토큰 상한·low 추론·입력 길이 제한 유지. 출력 한도를 더 줄이면 추론만 하다 잘릴 수 있어 이번에는 바꾸지 않습니다.
2. 요약 route `maxDuration = 300`: 인증·DB 조회·응답 처리 여유 확보. 이것은 Next.js 빌드에 담기는 실행 한도 요청이며 Vercel 설정/플랜을 자동으로 바꾸지 않습니다. Hobby는 Fluid compute 활성 시 최대 300초이므로 팀장 확인·재배포가 필요합니다.
3. UI: 세 기능 모두 최대 4분 대기와 취소 안내, 요약 처리 중 중복 실행 방지. 범위를 더 줄이라고만 하던 시간 초과 안내 수정.
4. 표준 앱 오류 JSON이 없는 HTTP 504도 안전하게 안내(`SERVER_TIMEOUT`). HTML/텍스트 원문은 노출하지 않으며 자동 재시도하지 않습니다. 이 코드는 인프라 시간 초과 가능성을 가리킬 뿐 원인을 확정하지 않습니다.
5. 시간 축소·가짜 HTTP 검사: 60초 지연을 60ms로 축소해 이전 25초 제한 실패, 새 240초 제한 성공을 확인합니다. 실제 60초 업체 응답의 재현 실험이 아닙니다. 요약·검색·추출 상수가 모두 240,000ms인지도 검사합니다.

관리자 `/api/ai/status` 연결 테스트도 추가 사용자 요청으로 240초를 적용하며 route `maxDuration = 300`을 명시했습니다. 화면은 최대 4분을 안내합니다. 성공을 보장하거나 생성 자체를 빠르게 하는 변경은 아닙니다.

## 배포본에서 확인할 것 — 팀장·사용자

1. 팀장: 새 커밋 배포 후 `/api/ai/summarize`의 실행 한도 및 Fluid compute 설정을 확인합니다. 공용 배포 설정은 직접 수정하지 않았습니다.
2. 사용자: 허용된 합성 대화가 있는 테스트 채널에서 **최근 10개 요약을 한 번** 실행합니다. 실패를 조사할 때에는 개발자도구 → Network → `summarize`에서 **경과 시간·HTTP 상태·error.code**만 확인합니다. 키·쿠키·요청/응답 원문·사내 대화를 공유하지 않습니다.
3. 약 25초에 `AI_TIMEOUT`이면 구버전 배포 또는 업체 408/504 가능성을 구분합니다. 새 버전에서도 업체 HTTP 408/504는 240초 이전에 반환될 수 있습니다.
4. `SERVER_TIMEOUT`이면 플랫폼/프록시 실행 한도·배포 로그를 팀장이 확인합니다. `AI_TIMEOUT`이 약 240초에 나면 앱 대기 한도 도달 가능성이 있습니다. 숫자 시각·상태·코드만으로 경계를 확인하고 원문 로깅은 피합니다.
5. 240초로도 지속되면 같은 요청을 반복하지 않습니다. 다음 단계는 제공업체 지연 확인, 별도 합의 후 최종 본문만 스트리밍(추론은 비노출), 더 빠른 모델 비교입니다. 스트리밍은 첫 표시를 개선할 수 있지만 추론/전체 생성 시간을 없애지는 않습니다. 다른 업체·유료 자동 전환·새 패키지 설치는 하지 않습니다.
